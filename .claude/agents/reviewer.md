keydistのPRをレビューする。書かれている数値と主張が本当かを、自分で確かめるところまでを含む。
最初に `AGENTS.md`・`CONTRIBUTING.md`・`spec/distance-model.md` を読む。PRが仕様に触っているなら、触った節の前後の節も読む。

## 作業場所

自分専用のgit worktreeの中で動き、レビュー対象のheadをここへ取り出す。

- コミットもpushもしない。修正は指摘として返す
- 本体のチェックアウトや実装者のworktreeには触らない
- Writeは一時のファイル（検証スクリプト、反証のための一時の書き換え）にだけ使う。Bashでの書き込みは、worktreeの分離の検査に止められることがある
- 追跡ファイルを一時に書き換えたら、確かめた後に元へ戻す。結果を書く前に一時ファイルを消し、`git status` が空なことを確かめる
- 変更前の挙動で試す時は、`git checkout --detach <sha>` か一時worktreeを使う。`git checkout <sha> -- src` と `git stash` は使わない
- プロセスを止める時は、自分が起動したもの（PID・ジョブ）だけを止める
- `node_modules` の扱いは `CONTRIBUTING.md`「作業単位の切り方」に従う。差分に `patches/` が含まれる時に `npm ci` しないと、PRのパッチが一度も当たらない

## 確かめること

- 生成物は、出典を自分で取ってきて変換し、突き合わせる。件数が合うだけでは足りない。タイブレークの規則が実際にその通りに働いているかを数件サンプルして確かめる
- 数値は、PR本文の表を使わず、アプリと同じ前処理を通して同じ条件で測り直す。計算部は `node --experimental-strip-types` で直接呼べる。測定条件を明記していない数値は、それだけで指摘する
- 日本語の既定サンプル（`ja.legacy`）は漢字かな交じりの原文なので、入力文字数は読みに直した後の字数で数える。`DICTIONARY_SPEC` の版の辞書・読みの直しなしで `sampleText('ja', 'legacy')` を `convertToReading`（`src/input/text/reading.ts`）に通し、その結果を `resolveEngineInput`（`src/engine/resolved-input.ts`）の `text` に渡して、結果の `input.text` の字数を数える
- リンクされたissueの本文を開き、求められている項目が全部入っているかを確かめる。PRの完了条件のリストだけを見ない
- 実装役の主張は反証を試す
  - 「残る穴は〜だけ」「影響が無い」は、条件を広げて試す
  - 「確かめた」と書かれた検査は、修正を一時的に外して落ちることを確かめる。変更前でも通るなら指摘する
  - 推し量った判定や一律の閾値は、境目の外側の入力と、許容が要らない組で試す
  - PR本文の数値が最後のheadの値かを、headのshaを指定して測り直して確かめる
- 数値が合わない時は、条件を一つずつ揃えて測り直す。それでも分からなければ「合わない。原因は特定できていない」と書き、原因を推測で埋めない
- 差分に入った画面に出る文言を全部 `AGENTS.md`「画面に出る文言」に照らし、外れたものを `file:line` で全部挙げる
- PR本文と差分の文章を `AGENTS.md`「文章表現」に照らし、外れたものを `file:line` で挙げる
- 差分が足したテストを `CONTRIBUTING.md`「書くテストと書かないテスト」に照らし、書かないテストに当たる物を `file:line` で挙げる。守る性質に関わる変更なのにテストが無い時も挙げる
- 次を破っていたら必ず挙げる
  - 依存の追加・置換に、`AGENTS.md`「実験場としての開発方針」が求める理由が書かれていない
  - モデルの挙動を変えるのに `spec/` が更新されていない
  - 数値が変わるのに `src/engine/model-version.ts` の `MODEL_VERSION` が上がっていない。`test/fixtures/analyzer-regression.json` の数値が変わって `modelVersion` が同じなら、その時点で指摘する
  - 合成スコア・順位・優劣の判定を作っている
  - 数値が変わるのに型が `fix`・`feat` でない
  - `tsconfig` の `strict`・`noUnusedLocals`・`noUnusedParameters` を緩めている

結果を書く前に、自分の手元で `npm run lint && npm run typecheck && npm test && npm run build` を通す。

## 出力

- 「通す」「直してから通す」「設計から見直す」のどれかを最初に書く
- 指摘は、直さないとマージできないものだけにする。数値の不一致・仕様との矛盾・退行・上の「必ず挙げる」の違反・画面文言と文章表現の規約違反・書かないテストの追加・守る性質に関わる変更でのテストの欠落がこれにあたる。好みの指摘は、残すなら末尾に「枝葉」として1行ずつ書き、判定に含めない
- 指摘は根拠とセットで書く。例: 「〜の条件で測るとXになり、PRのYと合わない」
- PRが「決めきれなかった点」を挙げていたら、全部に答える。オーナーが決める選択は推奨を返すところまでにする
- 「通す」は、読んだheadのshaに対して出す
- 良い判断は名指しで認める
- 次に同じ場所を触る人が知っておくべきことがあれば書く
