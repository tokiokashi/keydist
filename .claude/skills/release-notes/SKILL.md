# リリースノート

読者は一般の利用者。開発者やレビュアーではない。画面に出る文言の規則（`AGENTS.md`「画面に出る文言」）がそのまま効く。

手本は v0.2.0 のリリース（https://github.com/tokiokashi/keydist/releases/tag/v0.2.0。オーナーが作るまでは開けない）。基準の正はこのスキルの本文で、手本は後から直されることがある。形を写す前に、下の基準を読む。

## 何を書くか

- 利用者から見て何が変わったかで書く。コードの差分で書かない。main に入っていても利用者が辿り着けないもの（導線の無いページ等）は、その版の変更ではない
  - 書く前に、その版のトップページとサイドバーから実際に何が開けるかを確かめる
- 最初に意図を短く書く。なぜこう作ったか、この先どうなるか。機能の一覧より先に置く
- 画面を見れば分かることは書かない。ボタンの一覧、表の列、設定の項目は画面が説明している
- 触っても分からないことを書く。操作の効く範囲（全画面に効く・画面をまたいで残る）、戻し方（「元に戻す」で戻せる範囲）、共有 URL に入るもの・入らないもの、表示の読み方（軸の意味、要約の出どころ）、印や点が何を意味し、いつ消えるか
- できることを主語に書く。新しい機能は、読者がそもそもそれを知らない。「〜は含まない」「〜はまだ無い」から入らず、何ができるかを先に書き、制限はその後に短く添える
  - 例: 共有は「今の画面の URL をコピーする。解析設定を含むので同じ表示で開ける」を先に書き、「配列とテキストは含まない」はその後
  - まだ無い機能は、代わりにどこで使えるかと一緒に1項目にまとめる。保存が共有されない時はそのことも
- 細かい修正の羅列はしない。利用者の操作に効くものだけ、上の項目に溶かし込む
- 数値が変わるかは必ず書く。変わらないと書くなら、その根拠（回帰テスト・PR の記録）を確かめてから。推測で書かない（`AGENTS.md`「数値を扱う時・外に出す時」）

## 形

- 見出しは中身を指す名前にする。例: 「v0.2.0 での変更点」「新しい画面の対応範囲」「使い方の補足」「旧版」
  - 読者に語りかける見出しにしない。例: 「この版で何が変わるか」「知っておいてほしいこと」「触っただけでは分かりにくいところ」
- 話題ごとに `###` の小見出しを立て、その下は普通の文章で書く
  - 1つの小見出しの中で段落を分けない。改行が要る時は行末の `\` で改行する
- 箇条書きを太字の書き出し（`- **〜。** 本文`）で始めない。見出しなのか文なのか分からなくなる
- 箇条書きは、1項目1文で並べられる短い列挙（対応範囲など）にだけ使う
- 末尾に `**全ての変更**: https://github.com/tokiokashi/keydist/compare/v前の版...v今の版` を置く。前の版とつながらないタグ（`classic-final` 等）との比較リンクは置かない

## 手順

1. タグが打たれたことを確かめる（`git ls-remote --tags origin 'vX.Y.Z*'`）
2. 前の版のタグから今の版までにマージされた PR を洗い出し、利用者から見える変化を拾う。材料集めは調べ役に出してよいが、裏の取れないものは「未確認」として分けさせる
3. 下書きをオーナーに見せる。見出し・構成は版ごとに直されやすいので、公開前に必ず見せる
4. リリースは GitHub Releases に、そのタグを選んで作る。最新の版だけを latest にする
   - クラウドのセッションからはリリースを作れない（API が拒否する）。その時は本文をファイルで渡し、オーナーに貼ってもらう
