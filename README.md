# keydist

キーボードの論理配列を、モデル文章を打った時の**指の総移動距離**で評価するツールです。配列そのものの性質を数値で眺めるための道具で、優劣を判定するものではありません。

https://tokiokashi.github.io/keydist/

## 配列の書き方

文字 → 打鍵ステップ列で書きます。ステップの列が順次性を、ステップ内の集合が同時性を表します。
キーはQWERTY刻印で指す。

```json
"が": [["thumb-r", "f"]]   同時押し（1ステップ）
"が": [["shift"], ["f"]]  前置シフト（2ステップ）
"が": [["f"], ["shift"]]  後置シフト（2ステップ）
```

1本の指で複数キーを押す場合（キーの間を押す）は、その指の目標位置をキーの重心にしています。
ただし、同時押しのキーを別々の指で打つ選び方があるときは、その選び方を使います。

複数のシフト面を持つ配列は、`trigger`・`mode`・`rows` から同じ形式へ展開できる。
`rows` はQWERTYの4行で、セル配列を使えば `きゃ` のような複数文字の見出しも置ける。

```ts
{
  trigger: ['thumb-r'],
  mode: 'simultaneous',
  rows: [/* QWERTYの4行 */],
}
```

`mode` は `prefix` / `suffix` / `simultaneous` のいずれかです。面の展開後は直接書いた
`Sequence` と同じように評価されます。

旧定義や保存済み配列にある `space` は、右親指キー `thumb-r` のエイリアスとして受け付けます。

## 何を測るか

各打鍵について、その指がどこから動いてきたかを決めて距離を足し合わせます。

```
realized Stroke gap = 0  → d(前のキー, 今のキー)               同指連続
かなの位置の差 ΔI ≤ N   → min(d(前のキー, k), d(ホーム, k))    残る／戻るを比較
かなの位置の差 ΔI > N   → d(ホーム, 今のキー)                  復帰済み
```

`N` は、打つテキストの文字（かな）で数える先読みの文字数です。隣り合うかなは1、5文字先は5で、同じかなを打つ入力どうし
（`か` を打つ `k` と `a`）は0です。どの配列でも、同じ `N` がテキストの同じ範囲を指します。
入力が複数のかなを覆う時（`きゃ` を1回で打つ、ローマ字の `kya`、コンボが複数の綴りにまたがる等）は、その入力が覆う最後のかなから数えます。
配列に無く打てない文字も1文字と数えます。1入力がtrigger/outputなど複数Strokeへ
分割されても範囲は変わらないので、action groupingやcontinuous holdだけでは先読み範囲は変わりません。
担当する指が1本のキーだけの割り当てでは、`N` を増やすと比較できる候補が増えるので、総距離は減る方向に動きます。
担当する指が2本以上のキーを持つ割り当てでは、`N` を増やすと指の選び方も変わるので、総距離が増えることもあります。
ホームへの復帰移動そのものは距離に計上していません。指が自然にホームへ戻っていることを期待しているからです。

指の割り当ては、指ごとに担当するキーを決め、キーごとに基本の指を決めます。1つのキーを複数の指が担当できます。
担当する指が2本以上のキーは、`N` 文字先までの範囲で、次の順に最小になる指で打ったものとして測ります。
同指連続の数、指の左右の入れ替わり（隣の指が同じかなか直前のかなで打ったキーに対して、左右が逆か同じ横位置になる打鍵）の数、
同じ指が近くに戻る打鍵（同指連続でなく、同じ指が同じかなか直前のかなの中で別のキーを打っていた打鍵）の数、基本の指で打ったキーの数が多いこと、総移動距離の順で、
それでも同じなら指の固定の順です。範囲の中の最小は厳密に求めます。
この値は、複数の指で打ち分けられることを前提にした配列の性質で、実際のタイピングの再現ではありません。
総移動距離は後ろの方で比べるので、担当する指を足した割り当ての総移動距離が、足す前より長くなることがあります。
親指も親指キー以外のキーを担当できます。親指キーと親指キー以外のキーの間の距離は、キーの位置によらず1uです。
分割する物理配列（左右の手の間に間隔を空けた配列）では、キーと反対側の半分の手の指は、そのキーを追加で担当していても選びません。基本の指は外しません。
組み込みの指の割り当てには、既定とJISのそれぞれを元に、QWERTYで速く打つ人の打ち方に合わせて担当するキーを足した
「QWERTY最適化」「QWERTY最適化（JIS）」があります。打鍵再生では、各打鍵を打った指を示します。
キーの並びがQWERTYと同じ配列「QWERTY最適化」は、指の割り当ての推奨として、この割り当てを持ちます
（物理配列がJISなら「QWERTY最適化（JIS）」）。全体・Workspace・物理配列のレベルで別の割り当てを選んでいても、
配列「QWERTY最適化」は推奨の割り当てで測り、QWERTYと並べて比べられます。配列やSetupのレベルで選んだ割り当てが、推奨より優先されます。
指の割り当ての画面では、組み込みの割り当てを自作と同じ図で見られます（複数の指が担当するキーは、基本の指の色で塗り、追加の担当の指を帯で示します）。組み込みは編集できず、複製して編集します。

日本語のテキストに漢字が含まれる時は、評価の前に漢字を読み（ひらがな）に直します。読みは形態素解析の辞書（IPADIC）で求め、
読みに直した後のテキストで、入力文字数・先読みの位置・打鍵再生の表示を数えます。読みに直せない漢字（辞書に読みが無い語）と、
辞書を読み込めなかった時の漢字は、打てない文字として数えます。打てない文字の数は、読みに直せなかった漢字・記号・それ以外の文字に分けて出します。
読みは辞書の版で変わるので、読みに直した数値には辞書の名前と版を付けます。漢字を含まない日本語のテキストと英語のテキストでは、辞書を読み込みません。
読みは文脈バーの「読み」から語ごとに確かめて、直せます。読みが複数ある語は候補から選べ、どの語もひらがなと「ー」で読みを入力して直せます。
直しは表記の単位で、そのテキストの同じ表記の語すべてに当たります。直した読みはテキストと一緒に保存され、直した読みで測った数値には、読みを直したことと直した表記の数を付けます。

日本語のテキストは、既定では、かな・英数字と `、` `。` だけを評価します。ほかの記号は評価の前に取り除き、打てない文字の数にも数えません。
半角の `,` `.` は、配列が持たなければ `、` `。` として打ちます。条件で記号をすべて残すと、配列が打てない記号は打てない文字として数えます。英語のテキストは変わりません。全角の `！` `（` などは、日本語でも英語でも、対応する半角の記号と同じ記号として打ちます。

比較表は、距離とは別に、テキストを打った時に現れたBigramの組（続けて打つ2回の打鍵）が何種類あるかも出します。
前置・後置のシフトはそのシフトで打つ文字と合わせて1回の打鍵と数え、物理キーだけで数えた値とシフトを含めて数えた値を並べます。

詳細は [spec/distance-model.md](spec/distance-model.md)。

構造解析では、正規化したStrokeを手ごとの参加factで **Raw hand run** にまとめた後、
ChainInterpretationを適用して **Analysis Chain** を作ります。semantic normalization自体は
Chain境界を決めません。同指・trigger-only・逆手同時入力は独立したPolicy条件で、
親指だけのlayer/modifier操作を区切るかは未決のため推測していません。
ChainInterpretationは配列ごとの測定条件として数値のsnapshotにも残します。

条件（先読み `N`・物理配列・指の割当・ローマ字の綴り・Chain / Arpeggioの数え方など）は、
全体 → Workspace → 物理配列 → 打ち方 → 配列 → Setup の順に重ねて決まります。
Workspaceで変えた条件はそのWorkspaceに載ったペインの数値にだけ入り、単体ページや他のWorkspaceの数値は動きません。
Workspaceに値が無ければ、全体の条件だけで決まります。

Analysis Chain内の隣接Strokeからは、手ごとの **Transition fact** を作ります。
同時押しで1手に複数Pressがある場合もPress×Press候補を全部残し、指の内向き/外向き、
飛び指、親指、物理的な `dx/dy` を事実として保持します。この段階ではrollやArpeggioの可否を
決めません。同じ指のcandidateを持つTransitionはSFB eventとして数え、event数と
関与Strokeのcoverageは別に扱います。

3 Stroke内で指の方向が反転する場合は **RedirectEvent** として別に保持します。
同時押しのpivotでも実在する同じpivot Pressを通る反転pathがあればcandidateにでき、
candidateが複数でも1 windowのEventは1件です。別のpivot finger同士を継ぎ接ぎして
架空のredirectを作ることはありません。

そのTransition列からは、同じ方向へ3 Stroke以上続くmaximal区間を **LongRoll**、
LongRollに含まれない独立した2 Stroke pairを **TwoRoll** として保持します。
pure rollでは対象手の複数Press Strokeを除外し、output roleを持つ指だけを構成指にします。
親指もoutputなら構造上のRollからは消しません。TwoRollはend StrokeがRedirect pivotの時だけ
除外し、start側pivotは許容するという非対称な分類規則です。

keydistでいう **Arpeggio** はこのRoll自体ではなく、RollへPolicyを適用した派生区間です。
既定では親指coreを採用せず、同指連打のbridgeもredirect末尾の吸収も行いません。
Policyを有効にしても元のRoll / Redirect / SFB factは変更せず、ArpeggioSpanだけを拡張します。
同指bridgeを使う場合はsameを除いて同一方向が続く範囲をmaximal化し、その後で必要なら
末尾の逆方向1 Transitionだけをredirect tailとして追加します。

解析結果はさらにStroke単位の非排他的なAnnotationへ投影し、LongRoll / TwoRoll /
Arpeggio / Redirect pivot / SFBの所属を保持します。構造の「件数」はraw Event/Spanを数え、
「coverage」は重複をunionしたユニークStroke数で数えるため、overlapするArpeggioSpanを
coverageで二重計上しません。集計値には実効ChainInterpretation / ArpeggioInterpretationもsnapshotとして残します。

一般的なbigram / trigram / SFB / roll / redirect / alternationと、
keydist固有のRaw hand run / Analysis Chain / LongRoll / TwoRoll / RedirectEvent /
ArpeggioSpanの関係、raw countとcoverageの違いは
[docs/analysis-model.md](docs/analysis-model.md) にまとめています。

薙刀式には、センターシフトを出力キーと反対側の親指へ振り替える設定があります。既定は定義どおり右親指で、
設定をオンにすると片手だけの出力に対して逆側の親指を優先します。連続する同時押しシフトは、同じ親指キーが続く場合に
realized Stroke上の同指連続規則で親指が残った扱いになります。

物理配列は組み込みのロウスタッガード・オーソリニア・カラムスタッガード・オーソリニア（分割）で、それぞれANSIとJISがあり、選択欄では「US配列（ANSI）」「JIS配列」に分けて並びます。自作の物理配列を作る画面はありません。
JISかな配列は、JIS配列にしかないキー（`ー`・`む`・`ろ`など）を使うので、配列を対象にした時は、選んだ物理配列（全体・Workspaceの値）と同じ形のJISの物理配列で測ります（ANSIのオーソリニアならJISのオーソリニア）。
配列のレベルで選んだ物理配列とSetupの物理配列は、そのまま使います。選んだ物理配列に配列が使うキーが無い時は、計算せずに、JISの物理配列が要ることを表示します。
濁音・半濁音は、かなの後に濁点・半濁点のキーを打つ別のステップとして数えます（`が` は `か` と濁点の2ステップ）。
指の割り当てはサイドバーの「指の割り当て」で、組み込みを複製して編集します。ホームキーは配列ごとに任意指定でき、
省略時は物理配列の既定値を使います。比較表には、測定に使った物理配列と運指の名前を表示します。

## 出力

合成スコアは作っていません。次の項目を独立に出しています。

- 指ごと／全体の総移動距離
- 1打鍵あたりの平均移動距離
- 入力1文字（ローマ字展開・コンボ結合の前、かな・英字）あたりの平均移動距離。
  打鍵数はローマ字の綴り・コンボ・かな直接入力で配列ごとに変わるため、
  「1打鍵あたり」では打鍵数削減の効果が分母に吸収されて消える。
  文字数は展開前で固定するので、削減の効果はこちらに残る
- 入力1文字あたりのアクション（ステップ）数、および押下キー数。
  コンボ・同時押しで減った打鍵は、この2つに現れる。前者はまとめて打つほど下がる時間的なコスト、
  後者はキーを押す総回数（コンボでまとめても減らない）
- 単打面率。単打面に配置されている出力文字数 / 全出力文字数。
  1キーで「きゃ」のような複数文字を直接出力する場合は、その文字数ぶん分子へ入る
- 単打率。単打面の文字を出力するaction数 / 全action数。
  1キーで複数文字を直接出力しても1actionとして数え、ローマ字展開後の途中Strokeは含めない
- 1キー率。freshに押す物理キーが1つだけのaction数 / 全action数。
  output / trigger / held-trigger等の意味は見ず、realized Strokeの新規押下キー数だけを数える
- コンボ枠の見出しの数・命中した件数と、命中した延べ回数。コンボ枠に入るのは、配列のコンボ定義と、
  配列がコンボ枠に数えると宣言した面の出力。見出しの数は面の数ではなく、使える出力の数で数える。
  命中件数は「一度でも当たった見出し」の数、延べ回数はテキスト中で当たった回数を表す
- 面を持つ配列は、層ごとの押下数と全押下数に対する割合、およびヒートマップ（レイヤー）を出す。ヒートマップ（全部のレイヤーを合わせた図）とヒートマップ（レイヤー）は、別々のAnalyzerとして単体の画面とWorkspaceに出る。
  層・コンボごとの押下数と割合の表は、レイヤーとコンボの押下数のAnalyzerが出す。配列が持つ、キーを選んで出る文字を調べる図・修飾・コンボの一覧は、テキストに依らず配列の定義から出すキーマップのAnalyzerが別に出す（キーを選んで出る文字を調べる図が先頭）。
  コンボ枠は層とは別枠で集計する。文字キーを押しながら別の文字キーで打つ面は、配列が面ごとにどちらかを宣言する。
  かわせみ配列+は行指定キーの面を層に、二重母音拡張・左手コンボ拡張・トリガーが2キー以上の面をコンボ枠に数える。
  新小梅は文字キー同時押しの面をすべて層に数える。ヒートマップ（レイヤー）は層操作のための押下だけを色計算から除いて全層共通のスケールにし、
  文字トリガー同士の同時押下と薙刀式の合算表示では出力として扱うトリガー押下を色に残し、
  色の尺度は線形を標準として対数にも切り替えられる。
  ヒートマップ（レイヤー）の最大値は、タブで隠れた層も含めて全部の図で共通にする。ヒートマップ（全部のレイヤーを合わせた図）は常に線形
- キーごとの詳細（面 × 物理キー、面をまたいだ物理キー合算も）。押下数、押し方の内訳（出力・トリガー・押したままのトリガー）、
  直前の入力単位のかな（前の文字）、移動の起点の位置、距離の分布を、整数の回数で出す。
  面はコンボの面も含む。1つの打鍵が複数のキーを持つ時は、各キーに1回ずつ数える
  レイヤーをまとめて見せる図は、まとめた面の値を量ごとに足して出す
- 打鍵再生のAnalyzerでは、選んだテキストの打鍵を1ステップずつ再生できる。再生・一時停止・停止・ステップ送り・
  速度変更・シークに対応し、同指連続の距離ディレイ、直近の実効アクション/秒、
  同指連続のキー移動アニメーション、チェーンの表示も切り替えられる。
  日本語のテキストの読点・句点の前後には、打鍵とは別の待機時間（ミリ秒、既定は0）を足せる。
  打鍵時間（待機を除く）と総時間（待機を含む）を分けて出し、かな/秒・アクション/秒は待機を含む表示時間で求める。
  サイドバーの「個人速度」で、通常のアクション/秒・同じ手の別指の組ごとの交互打鍵速度・指ごとの同じキーを続けて打つ速さ [アクション/秒] と移動の時間 [ミリ秒/u]（同じ列の下段のキーとの往復と、ホームキーを続けて打つ時間の差から求める）・同時押し（両手・片手・親指）の上乗せ [ms] を測定し、組ごとの結果を保存して再生へ反映できる
- **Analysis Chain** と **ArpeggioSpan** は構造解析済みの区間をそのまま再生図へ投影する。
  表示側ではChain / Arpeggioを再判定しない。Chain境界とArpeggioInterpretationは条件のモーダルから編集でき、
  ArpeggioInterpretationは output親指・same bridge・redirect tail の3項目だけを持つ
- 配列 × 指のマトリックス（画面の名前は「指ごとの比較」）として、指ごとの移動距離 [u/文字]、押下数 [押下/文字]、
  指間距離の平均 [u]、指間距離の標準偏差 [u] を並べて出す。移動距離と押下数は入力1文字あたりに直した値を表に出し、
  1文字あたりに直す前の生の値はツールチップで出す
- 同指連続の指ごとの内訳（配列 × 指のマトリックスの面）。Press（1本の指の1回の押下）単位で、回数・その指のPressに対する比率・全体の同指連続に対する割合を出す。
  同時押しで1本の指が複数キーを押してもPressは1回と数えるので、比率の分母は押下数の面とは違う量になる。
  比率はその指のPressが0回、割合は全体の同指連続が0回のとき、0%ではなく「—」を出し、ツールチップに分子と分母の回数を出す
- 指ごとの距離。見る量を1つ選んで、左手の小指から右手の小指の並びの縦棒グラフで出す。指ごと（親指を含む10本）は移動距離と押下数、隣り合う指6組は指間距離の標準偏差・平均・最大。割合はツールチップに出す。
  隣り合う指6組の量を見ている時は、その下に6組それぞれの指間距離の分布を、状態ごとの割合 [%] の棒グラフで出す。
  状態は指間距離（両方がホームにある時の距離を引いた値）を小数第6位に丸めた値で、割合の分母は平均・標準偏差と同じ全打鍵（その組の指がホームにある打鍵も含む）
- 右手の距離の割合・右手の押下の割合（比較表の2列。右手は親指を含む5本。右手の指ごとの総移動距離の合計 / 全指の総移動距離、右手の押下数の合計 / 全押下数。左手は100%から引いて読む）
- Bigramの組の種類数（比較表の2列）。テキストを打った時に実際に現れた、続けて打つ2回の打鍵の組が何種類あるか。配列の全キーから作れる組の数は出さない。
  前置・後置のシフトは、そのシフトで打つ文字と合わせて1回の打鍵と数える。組は順序つき（A→BとB→Aは別）で、親指のキーも数える。
  物理キーだけで数えた値と、シフトを含めて（左右のシフトと左右の親指シフトも区別して）数えた値を並べる
- 同指連続回数と比率
- 指間距離の平均と実測最大値（隣り合う2本の指の距離を全打鍵で平均し、両方がホームにある時の距離を引いた値。両指ともホームから一度も動かなければ0。標準偏差はばらつきとして併記。平均と標準偏差を読む補助として、状態ごとの頻度の分布も出す）
- `N` を振った時の総移動距離の変化

## 何を測っていないか

- 出てきた数字を絶対値として評価することは難しいと考えています。現在自分が使っている配列の数字と相対比較して他の配列の特性をイメージするといった用途に向いていると考えています
- タイピングという2次元的な動きを距離という1次元に圧縮しています
- 全ての計算は指がホームポジションにあるのが良いということを前提としています。配列の作成時にホームキーを指定でき、未指定なら物理配列の既定値を使います
- 指の長さや手の動きなどの個人差のある部分は意図的にモデルから排除しています。あくまで配列の押すキーの解析情報と捉えてください
- 同じ理由で「指の疲れ」等を導出することはありません。指の特性や係数など全ての項目をフィッティングすることは困難と考えるためです。疲労を考えたい人は移動距離や指間距離などの数値の傾向から相対的に判断してください
- 指の割り当ての最適化はありません。どの指がどのキーを担当するかは利用者が決め、「指の割り当て」の画面で明示的に設定できます。モデルが選ぶのは、複数の指が担当するキーをどの指で打つかだけで、担当の範囲の中で `N` 文字先まで、同指連続の数、指の左右の入れ替わりの数、同じ指が近くに戻る打鍵の数、基本の指で打ったキーの数、総移動距離の順に比べて最小になる指です。総移動距離を最優先には最小にしないので、担当する指を足すと総移動距離が長くなることがあります。薙刀式のセンターシフトに限り、設定で左右の親指を振り替えられます
- 連続打鍵以外のホームへ戻る移動は距離に含んでいません。指が自然にホームに戻っていることを期待しているからです。中段以外に指を置いた方が楽な配列（QWERTYなど）では、配列の作成画面でホームキーを明示指定してください
- 物理配列と論理配列は結びついているので、物理配列を入れ替えてみて同数字が動くのかを考えてみてください

コンボを加えた実測では、移動の多い配列で距離が減り、移動がすでに最小化された配列ではむしろ増えます。

測定条件: かな1676文字 / `N` = 3 / ロウスタッガード / 指の割り当ては既定 / 綴りは**訓令式**。コンボありは、TK音直入力法のコンボ定義を各配列に足して測っています。
上の表は、漢字を含まない現代文の自作文（サンプル欄の「現代文」）で測っています。既定の日本語サンプルは、夏目漱石『吾輩は猫である』の冒頭（青空文庫の原文）で、漢字を読みに直して評価します。
これは自作の例文なので、実際の文書の統計とは異なります。書き手の語彙や文体の癖が数値に残るため、実際の文書を代表するものではありません。
綴りは配列と対で効くので、大西配列を大西式綴り（`sh` / `ji`）で打つと別の値になります
（新サンプルではコンボなしで1041u、同指連続32）。

| 配列 | コンボなし | コンボあり | 同指連続 |
|---|---|---|---|
| QWERTY | 1915u | 1764u | 238 → 231 |
| Colemak-DH | 986u | 1047u | 42 → 117 |
| 大西配列 | 1049u | 1058u | 38 → 75 |

総距離だけを見て「コンボは効果がない」と読まないでください。打鍵数の削減は
「入力1文字あたりのアクション数」（[出力](#出力)参照）の側に直接出るので、
指標としてはそちらを見てください。

ローマ字配列のコンボは、定義ごとの発火条件に従います。現時点で拗音限定（`youonOnly`）なのは
TK音直入力法のコンボのヤ行19件で、拗音のローマ字塊の内部で直前に子音がある場合だけ発火します。
そのため、`きゃ` の `ya` はコンボになりますが、単独の `や` は `y` + `a` に分かれます。

コンボ定義は適用範囲も持てます。TK音直入力法のコンボはどれも `site` `desu` のようなローマ字の綴りを
出すので、かなをローマ字に展開した区間だけで使い（`romajiOnly`）、英文や、日本語テキストに混ざった英字の区間では使いません。
配列は1つで、英文を選んだ時はコンボの無い単打配置として測ります。

詳細は [spec/distance-model.md §12](spec/distance-model.md#12-数値の性質)。

## 日本語

同じかなテキストを、ローマ字配列にもかな配列にも食わせて比較できます。

- **ローマ字配列** — かな → ローマ字のテーブルを通してから打つ。
  テーブルは配列と独立しており、既定配列ごとに別の綴りを割り当てられる。
  促音は差し替え後の綴りから展開する（`っか` → `kka`、`し` を `shi` にすれば `っし` → `sshi`）
- **かな配列** — かな → 打鍵ステップ列を直接持つ。テーブルを通さない

どちらも最終形は打鍵ステップ列なので、評価器は両者を区別していません。

入っている日本語向けの配列:

| 配列 | 出典 |
|---|---|
| 大西配列 | 公式配置。公式が前提とする綴り（シャ行 `sh` / じ `ji` / じゃ行 `j`）で打つ |
| TK音直入力法 | 下段を差し替えた版に、Vialキーマップのコンボ73件を適用。綴りは訓令式。コンボは日本語をローマ字で打つ時だけ使い、英文は同じ配列の単打配置だけで打つ |
| 薙刀式v18 | [公式配布のDvorakJ定義](https://oookaworks.seesaa.net/article/456099128.html)から機械的に生成 |
| 親指シフト（NICOLA） | [NICOLA配列規格書](http://nicola.sunicom.co.jp/spec/kikaku.htm)を仕様根拠として実装。専用キーボードの配置をANSIに写しているため、距離の絶対値は参考値 |
| 新下駄 | [考案者kouy氏の公開配列表](https://kouy.exblog.jp/13627994/)を仕様根拠として実装した7面の同時打鍵配列 |
| 月配列2-263式 | [成立時の2-263式配列表](https://jisx6004.client.jp/data/2chlog/1055763380.html)と[月配列の解説](https://jisx6004.client.jp/tsuki.html)を仕様根拠として実装した中指前置シフト配列 |
| JISかな配列 | JIS X 6002で策定されたかな配列。キーの割り当ては、xkeyboard-configの `symbols/jp` の `kana` と照合して一致を確かめた。Shiftで小書きのかな・`を`・`「」`・句読点を打ち、濁点・半濁点はかなの後に打つ。JISの物理配列が要る（選んだ物理配列と同じ形のJISで測る） |
| かわせみ配列+ | [公式Kikyo定義](https://github.com/semialt/kawasemi/blob/911bb8f/Kikyo/%E3%81%8B%E3%82%8F%E3%81%9B%E3%81%BF%E9%85%8D%E5%88%97%2B.kky)から移植（コミット `911bb8f`、blob `220851f`）。二重母音・くき・つち・左手コンボ拡張を含む |

コンボは「出力する文字列 → その文字を出すキーの集合」で書きます。
キーを物理位置ではなく文字で指すので、同じ定義を別の英字配列にも適用できます。

ローマ字の綴りは配列と対で意味を持ちます。大西配列は上段と中段の同じ列に `y` と `s` が並ぶため、
`sya` が同指連続になります。`sha` なら `h` が隣の列に来て指が分かれます。
同じ綴り替えをQWERTYに適用しても効果は出ません。

入っているローマ字の綴り:

| 綴り | 内容 |
|---|---|
| 標準 | QWERTY向け。ジャ行 `j`、シャ行 `sh`、チャ行 `ch` を使う（初期割り当ては訓令式） |
| 訓令式 | 1かな1綴りの素のローマ字（`si` / `sya` / `zi` / `zya`） |
| 大西式 | 大西配列公式が前提とする綴り（`si` / `sha` / `ji` / `ja`） |
| AZIK | 拡張ローマ字。二重母音・撥音・促音をまとめて1綴りに落とし、打鍵数を削る（`かん` → `kz`、`きゃん` → `kyz` など）。促音は `;` の1打。[出典](https://github.com/toriwasa/azik-roman-table)の `azik_romantable.txt` から機械的に生成（`scripts/gen-azik-romaji.ts`） |

サイドバーの「ローマ字の綴り」から、組み込みの綴りを基底にした差分を保存できます。
綴りが割れるかなごとに綴りを選べ、一覧に無いかなの綴りも足せます。促音の自動生成の有無も綴りごとに設定できます。

## 自作の配列を足す

サイドバーの「ローマ字配列」から、段ごとに文字を並べて入れる。

- 数字段は空でよい。空ならQWERTYのものを使う
- 各段に置ける数は物理配列で決まる（ANSIなら12 / 12 / 11 / 10）。超えると弾く
- 同じ文字を複数のキーに置いてもよい。打鍵には先に書いた方を使い、
  後の方は刻印だけ残す
- 英字の配列では、大文字と記号を組み込みの英字配列と同じくShiftとの同時押しで打つ。
  `A` や `!` など、Shiftを使わずに打てるキーへ自分で置いた文字は、置いた定義を使う
- ローマ字の綴りを選べる。綴りは配列と対で効くので、配置に合う方を選ぶ。自作の綴りは
  「ローマ字の綴り」から作成して選ぶ

自作した配列はそのブラウザのlocalStorageにだけ保存しています。

## 既知の制限

- 大文字のシフトは配列に含んでいません。要望が多ければ機能追加検討します
- キーの入れ替えとローマ字定義で実現できる配列は「ローマ字配列」の画面で定義可能です
- 変換操作（変換キー・確定・文節移動）は打鍵列に含めていません。打ち手による差が大きく、配列間では共通のためです
- 担当する指が1本のキーだけの割り当てでは、出力される総移動距離は**下界**です。窓の内側では常に小さい方を採るため、実際の運指はこれ以上になります。担当する指が2本以上のキーを持つ割り当てでは、指を総移動距離が最小になるようには選ばないため、下界と言えるのは、選んだ指の下で指を残すかホームへ戻すかを比べる部分だけです。担当する指を足すと総移動距離が長くなることがあります

## 開発

Node.js 22.20以上（24系なら24.4以上）が要ります（ビルド時の検査が使うAPIがそれ以降にしか無いため）。

```bash
npm install
npm run dev        # 開発サーバー
npm test           # モデルの分岐を検証
npm run lint       # 書式と一般的な誤りの検査
npm run format     # 書式を整える
npm run typecheck  # 型検査のみ
npm run build      # ビルドのみ（型検査はしない）
```

コミット規約・ブランチ運用は [CONTRIBUTING.md](CONTRIBUTING.md)にあります。
clone直後に `git config core.hooksPath .githooks` を1度実行してください。

## 数値の出どころについて

本リポジトリが出力した数値と、改変版や第三者のツールが出力した数値は、直接比較できるものではありません。
keydist の数値として示されたものについて回答できるのは、本リポジトリの出力に限ります。

本リポジトリの数値は、選択した条件のもとでの結果にすぎません。
他の方が作った配列やツールについて論じる際は、条件（物理配列・運指・ホーム・条件差分）も併記してください。
設定が違えば同じ配列でも数値は変わります。

このツールは数値を出すだけで、配列の優劣は判定しません。
数値からどういった結論に至るかはご自身の判断であり、このツールはそれを誘導しません。
複数の指標を並べているのは、どれを重く見るかが人によって違うためです。
