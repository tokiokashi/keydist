# ADR-0003: 条件をポリシー・解釈・解析設定の3種類に分ける

- 番号: ADR-0003
- 日付: 2026-10-06（取り込みの日。決めた日は読めない。READMEの「日付」を参照）
- 状態: 採用（解釈の持ち主は、ADR-0004が一部を解析設定へ絞っている）

## 背景

決めた当時の議論と理由は、取り込み前の履歴にあり読めない。以下は、`docs/architecture.md`・`spec/`・コードに書かれている内容に限る。

## 決定

設定を3種類に分ける。「その値を変えると、同じ名前の数値の意味が変わるか」と「今いくつのAnalyzerが読むか」で判定する（`docs/architecture.md` 「流れ」）。

| 種類 | 何を決めるか | 持ち主 |
|---|---|---|
| ポリシー | Traceの中身 | カスケード |
| 解釈 | Traceは同じまま、複数のAnalyzerが読む数値の定義 | カスケード（全体とWorkspaceのレベル） |
| 解析設定 | どの数値をどう見せるか | Analyzerのインスタンス |

- カスケードは、全体 → Workspace → 物理配列 → 打ち方 → 配列 → Setupの順に上書きして実効値を求める（`spec/distance-model.md` §12.3「条件の解決順」、`src/input/settings/levels.ts`）
- 解釈は、全体とWorkspaceのレベルにだけ置く。配列・Setupごとの上書きは持たない。Traceは同じまま数値の定義だけが変わり、Workspaceの中のペインは同じ条件で並ぶため（`spec/distance-model.md` §12.3）
- 指の割当は、この分類ではポリシーと同じ扱いになる。`docs/architecture.md` 「流れ」は、Traceの中身を変え、持ち主はカスケードだからと書いている。型は `TracePolicy` ではなく独立した `FingerAssignment` で、物理配列と合成した `Geometry` として `generateTrace` へ渡る（同節）
- 解釈の型を指して「ポリシー」と呼ばない（`ChainPolicy` / `ArpeggioPolicy` は使わない語）

## 却下した案

- 解釈を配列ごと・Setupごとに上書きできるようにする案は、置けるレベルから外している。書かれている理由は、Traceは同じまま数値の定義だけが変わり、Workspaceの中のペインは同じ条件で並ぶこと（`spec/distance-model.md` §12.3）だけ
- 3種類以外の分け方を比べた記録は読み取れない

## 結果

- 条件に置いた設定は、条件が数値に付随する仕組み（ADR-0010）に乗せる
- 設定を足す時の置き場は、`AGENTS.md` 「設定項目を足すか決める」の「置き場」がこの分類を使う
- 時間モデルと速度の平均は、初めは解釈としてカスケードに置かれていた。今1つのAnalyzerだけが読むので、後に解析設定へ移した（ADR-0004）
