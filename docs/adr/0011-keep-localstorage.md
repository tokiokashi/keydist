# ADR-0011: 資産の保存をlocalStorageのまま続ける

- 番号: ADR-0011
- 日付: 2026-11-10（issue #26、コミット `4ddd1ef0`）
- 状態: 採用

## 背景

資産と設定は、キーごとに別の文字列としてlocalStorageへ保存する（`keydist:` で始まるキー）。
issue #26は、実際のサイズを測り、IndexedDBへ移す必要があるかを判断して記録することを受け入れ条件に挙げていた。

## 決定

IndexedDBへ移さず、localStorageのまま続ける。判断の根拠は、`docs/architecture.md` 「保存容量の見積もり」に、`scripts/measure-storage-size.ts` で測った値とあわせて書かれている。

- 構造を持つ資産と組み込みのテキストは、全部写しても合計19.6万字ほどで、枠（ChromiumのlocalStorageの約524万字）の約3.7%に収まる
- 長いテキストは、全文の大きさ（約32万字）で1件につき枠の約6%を使い、枠には約16件入る。使い切る前に、容量の超過の知らせが出る
- 丸ごと直列化・復元する時間は、全文の大きさのテキスト16件で、直列化が約26ms、復元が約10ms（Node v22.23.4、Intel Xeon 2.10GHz 4コア、各7回の中央値）
- 容量の超過で書けなかった時は、保存できなかった資産と保存データの大きさ（大きい順）を画面に出す
- 書き出しファイルの読み込める大きさの上限は、16MiBのままにする

## 却下した案

- IndexedDBへ移す案は、今は採らない。移すと読み書きが非同期になり、`commitCommand` が書き込みの直前に同期で手持ちを追いつかせる前提（`app/standalone/asset-syncs.ts`）と、タブ間の追従が組み直しになる。一方で、構造を持つ資産は枠に対して小さい
- 移す動機になるのは、テキストを枠に入りきらないほど長く何件も持つ使い方が出た時で、その時に後続として扱う

## 結果

- この判断は、Chromiumだけの測定に基づく。Safari・Firefoxの枠は測っていない
- 容量の超過は、画面の知らせで利用者に見える。黙ってデータを失わない
- 全データの書き出しと復元（issue #26）が、同じコミットで入った。別のブラウザへ全データを移せる
- この節の数値は `docs/architecture.md` の記載の引用で、このADRを書いた時に測り直していない
