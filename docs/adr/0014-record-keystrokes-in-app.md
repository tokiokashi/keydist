# ADR-0014: 打鍵の記録はアプリの中で取り、外のツールの記録は読み込まない

- 番号: ADR-0014
- 日付: 2026-11-15
- 状態: 採用

## 背景

実際に打った時の打鍵の間隔を、Run Chartと同じ横軸（評価に渡したテキストの文字位置）に並べて、指標の大きい箇所や文節の区切りと突き合わせたい。
そのために、ストロークごとの時刻を持つ記録が要る。

外のツール（打鍵を記録するソフトや、タイピングサイト）の記録を読み込む案では、次の2点を詰める必要があった。

- 記録した配列を、keydistの配列定義に対応づける
- 打鍵を、評価に渡したテキストの位置に対応づける

個人速度の「文章を打つ測定」（`spec/playback-timing.md` §6.4）は、示す文を打たせ、打鍵の照合・ローマ字の綴りの受け付け・コンボの読み方の判定・取れるキーの規則をすでに持つ。
この測定は、短い文を複数本、各3回打つ前提で、境を入れず、全体のレベルの条件だけで打鍵の列を作る。

## 決定

記録はアプリの中で取る。利用者が選んだ評価テキストの範囲を、選んだ配列・物理配列・指の割り当てで打ち、ストロークごとの時刻を残す（`spec/keystroke-record.md`）。
外のツールの記録は読み込まない。

- **照合の規則は§6.4を流用する。** 新しい照合の規則を作らない。打鍵の列の作り方だけを、Run Chartと同じ経路（Setupと全レベルの条件、コンボを止める境を含む）にする。§6.4の経路は境を入れず、Setupを受け取らないので、Run Chartの点の位置と合わない
- **記録の単位は約1000字の範囲にする。** 全文を1回で打たせると長すぎる。範囲は `src/input/text/display-ranges.ts` のものを使い、範囲ごとに打てるかを判定する。打てない文字を飛ばして記録する形は採らない（飛ばすと、打っていない文字の位置が記録の穴になる）
- **ストロークが属する位置は `e` で持つ。** Run Chartの点の横位置と同じ定義（`src/interpretation/selection-ends.ts`）を、両者が共有する。条件の規則の綴りで打った記録の `e` の集合が、Run Chartの点の位置と等しいことを検査する
- **ローマ字の綴りは、かなごとに打った綴り `typed` を記録に持つ。** 打っている間は、文の単位の窓で打鍵の列を作り直し、保存する時に全文で1度だけ作り直して照らし合わせる。窓の作り直しは、§6.4の「文全体の作り直し」からの意図した逸脱である
- **保存は、他の資産と別のキーに置き、データ・設定の管理の書き出しファイルには入れない。** 記録だけを書き出す・読み込むファイルを別に持つ。画面は、他の画面と同じ個別画面の枠で、個人速度の画面とは別の `/record` に置く
- **改行と空白は、打たない文字として打てない判定から外す。** 同梱の評価テキストは、本文を作る時に空白類を落とすので、残る空白は英数字の間の半角空白だけである。半角空白を打てない配列（NICOLA）では、その空白が飛ばされ、数えると範囲が打てなくなる。改行と全角空白を残す利用者のテキストでも同じになる。同梱のcorpus/の14本を読みに直した本文で打てる範囲は、QWERTY（訓令式）では数える時も数えない時も58/140で、NICOLAでは数える時の60/140が数えないと73/140になる。読めない漢字など他の飛ばされた文字は、今までどおり範囲を止める
- **記録を図に出すこと・集計は、この判断の範囲外とする。**

## 却下した案

- **外のツールの記録を読み込む。** 2点の対応づけが、記録の形式ごとに要る。各ツールの記録の形式は調べていない。アプリの中で取れば、打った綴りで作った打鍵の列から、2点とも決められる
- **個人速度の画面に節を足す。** 個人速度は、配列にもテキストにも紐づかない1つの値である。記録はテキストと配列に紐づき、保存の単位も複数件で別になる。キー入力の取り方（`key-capture.ts`）と文章を打つ測定の部品は共有できるので、画面だけを別にした
- **示す文を打つ測定の経路（§6.4の打鍵の列）で記録を作る。** 境を入れず、Setupを受け取らないため、同じ条件のRun Chartの点の位置と一致しない
- **打っている間も全文で作り直す。** 全文の打鍵の列を作る時間は、ひらがなの文を繰り返した10万字で2.14秒、30万字で5.60秒（QWERTY・訓令式、`recordBaseTrace`を3回測った中央値、Node v22.23.4、Intel Xeon 2.10GHz 4コア）で、綴りを変えるたびに待たせることになる。1打ごとの応答に間に合わないので、窓で作り直し、保存する時だけ全文で検証する
- **記録を書き出しファイル（`keydist-user-assets`）に入れる。** 記録は1件約17KB（`docs/architecture.md`「保存容量の見積もり」）で、種類ごとの件数の上限（100件）まで入れると約1.7MBが加わる。書き出しの上限の前提（全データを入れても最大が変わらない）が変わるため、別のファイルにした
- **時刻を絶対の値（ミリ秒）で持つ。** 1件の大きさが約1.4倍になる（時刻の差を0.1ミリ秒の整数で持つ形と、同じ記録で比べた値。1000字の範囲・1764打で23,606字と17,405字（キーの列の照合値を足す前の値））

## 結果

- 記録の `e` の集合とRun Chartの点の位置が等しいことを `test/keystroke-record-run-chart.test.ts` が確かめる
- 記録が保存できる件数は、localStorageの枠で決まる（1件約17.4K字で、枠の約524万字を記録だけで使うと約300件。他の資産が使う分だけ減る）。16MiBのファイルの上限と100件の上限は、記録のファイルでは先に届かない
- 窓の作り直しと全文の作り直しが食い違う範囲は保存できない。食い違う範囲の割合は測っていない
