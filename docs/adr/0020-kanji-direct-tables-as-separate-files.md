# ADR-0020: 漢直の組み込みの配列の表を独立したファイルで配り、配列を使う時に取得する

- 番号: ADR-0020
- 日付: 2026-11-21
- 状態: 採用

## 背景

ADR-0019は、TUT-Codeを足した時点で漢直の表の遅延読み込みを採らず、バンドルサイズの上限を引き上げた。同じADRは、漢直の配列がさらに増える時に比べ直すと記録している。ADR-0019の判断のうち、バンドルの上限と遅延読み込みを採らないことをこのADRが置き換える。ADR-0019のほかの判断（Aモードの表・空白キーの扱い）はそのまま有効なので、ADR-0019の状態は `採用` のままにする。

漢直の雪華（別のissueで足す）は、単字約3700字に加えて熟語約2.4万語の表を持つ。作者のリポジトリの表から、見出しと記号の並びの組をJSONの配列にしてgzip（レベル9）で縮めると、単字は約22KB、熟語は約190KBになる。今の作りでは、組み込みの配列の表がすべてJavaScriptに入り、計算用Workerと各ページの初期読み込みの両方に含まれる。#887（TUT-Code）のheadで測ったgzipは、計算用Workerが100707B（上限102000B）、JavaScript全体が965611B（上限970000B）、個別画面（ヒートマップ）の初期読み込みJSが406382B（上限410000B）で、残る余白は1〜4KBだった。雪華は上限に入らない。

組み込みの評価テキストの本文（`src/platform/corpus/`）と読みの辞書（`src/platform/reading/`）は、JavaScript以外のファイルとして配り、選ばれた時に取得する前例である。

決めることは次の4つだった。

1. 対象の配列と、表を配る形
2. 表を取得する前に出せるもの
3. 取得を待つ間と、失敗した時の扱い
4. 性能の予算の項目

## 決定

1. 漢直の配列（今はT-CodeとTUT-Code）の表を `src/input/layouts/tables/*.json` として配り、配列が計算に使われる時に取得する。かな配列と英字配列は表が小さいので、今の作りのままにする。取得は `src/platform/layouts/kanji-direct-loader.ts` が持ち、取得した表は `src/input/layouts/kanji-direct-tables.ts` に置く
2. 表を取得する前の配列は、名前・別名・使う物理キーを宣言から持つ `Layout`（`pendingTable` 付き。表由来の項目は空）にする。`LAYOUT_BY_ID` に入るのはこの配列で、配列の一覧・検索・選択と物理配列の選択は、表の取得を待たない。漢直であること（`isKanjiDirectLayout`）と使う物理キー（`physicalKeysUsedByLayout`）は、この配列では宣言を読む。宣言が表から導いた値と一致することは、各配列のunit testが確かめる
3. `resolveEngineInput` は、取得する前の配列に `layout-table` の失敗を返し、計算をしない。ペインは取得中なら読み込み中を、取得に失敗したらエラーの文を出し、他の配列の数値は出す。取得は `resolvePaneInput` が始める。取得に失敗した配列は、対象の選択で配列を選び直した時（Testerは配列の選択）に取得し直し、それまで試し直さない。ページを開き直した時も取得し直す。Testerは `use-kanji-direct-layout.ts` で同じ状態を扱う
4. `scripts/measure-bundle.ts` に、配る表のうち最も大きい1ファイルのgzipを測る項目を足し、`scripts/bundle-budget.json` に上限を置く。新しい項目の上限は、`CONTRIBUTING.md`「性能の予算」の決め方（gzipサイズの1.1倍を1000 byte単位に切り上げた値）で決める。表を外した既存の項目は、表を外した後のサイズに同じ決め方を当てた値が今の上限より小さい時だけ、その値に下げる

## 却下した案

| 案 | 初期読み込み | JavaScript全体 | 採否 |
|---|---|---|---|
| 表をJSONのファイルで配り、選んだ時に取得する | 増えない | 増えない | 採る |
| 表を動的importのJavaScriptのチャンクにする | 増えない | 雪華だけで約210KB増え、上限に入らない | 採らない。`measure-bundle.ts` の「JavaScript全体」は遅延読み込みのチャンクも足すので、雪華が上限に入らない問題が残る |
| 予算の上限を引き上げる | 雪華だけで全画面が約210KB増える | 同じく増える | 採らない。漢直を使わない利用者も読み込みを待つ |
| 取得する前の配列を `Layout` とは別の宣言の写像で持ち、配列を引く場所が2つの写像を引く | | | 採らない。配列の一覧・検索・名前の表示・Setupと共有リンクの参照の確認など、`SetupCatalog.layouts` の写像を引く・受け取る `src/` のファイルが24あり（テストを除く）、それぞれが2つの写像を合わせて引く必要がある。表を取得する前の配列を同じ写像に入れれば、計算に使う場所（`resolveEngineInput`）だけが取得の状態を見る |

## 結果

- 計算用Workerと各ページのJavaScriptに、T-CodeとTUT-Codeの表が入らない。ビルドの後に `scripts/check-kanji-direct-assets.ts` が、表の断片が公開物のどの `.js` にも無いことと、同じ内容の独立したファイルが `assets/` にあることを確かめる
- 取得する前の配列は、表由来の項目が空の `Layout` なので、計算・図の表示にそのまま渡すと表が空のまま動く。`resolveEngineInput` が `pendingTable` 付きの配列を拒み、Testerは取得するまで入力欄を出さない。ほかの場所（配列の一覧の名前・別名・種類・使う物理キー）は宣言だけを読む
- unit test・スクリプトは、ブラウザで取得する表を `test/kanji-direct-tables.ts` がディスクから置く。表を取得する前の配列を使う検査（`src/engine/layout-table-wait.test.ts`）は、この補助をimportしない
- `test/fixtures/analyzer-regression.json` は変わらない（T-CodeとTUT-Codeの数値は動かない）
