# ADR-0022: 表から作った配列は識別子でキーに入れ、Workerへは表を送る

- 番号: ADR-0022
- 日付: 2026-11-28
- 状態: 採用

## 背景

雪華のように表から作る漢直の配列（ADR-0020）は、`Layout` として数十MBある（雪華で、構造化複製が35.9MB、Traceのキーの文字列が53MB）。
`Layout` をそのままキャッシュのキーに畳み込み、Workerへの依頼に載せる作りだったので、雪華を選ぶと、画面のスレッドが次の処理で止まった。

- Traceのキーの文字列化と、それを畳み込む解釈・抽出のキーの文字列化
- 依頼のたびの `Layout` の構造化複製。Workerは複製からもう一度キーを作るので、配列のオブジェクトで引くキャッシュにも当たらない

## 決定

- 表から作った配列には、配列のidと表の中身から決まる識別子を持たせる（`src/input/layouts/table-identity.ts`）。識別子は配列のオブジェクトに結びつけ、付けられるのは `tableLayoutWithIdentity` だけにする
- Traceのキーは、識別子を持つ配列では識別子だけを入れる（`src/engine/keys.ts`）。識別子を持たない配列は、今までどおり中身を入れる
- 配列を派生させる（`{ ...layout }`・コンボの重ね合わせ・ローマ字表の付与など）と、別のオブジェクトになるので識別子を持たない。派生で中身が変わっても、識別子が残って古い結果を返す事は起きない
- Workerへは、識別子を持つ配列そのものではなく、配列を作った表（雪華で378KB）を、Workerごとに1度だけ送る。Workerは同じ宣言の関数で配列を作り、識別子ごとに持つ。2度目からは識別子だけを送る。Workerが作った配列の識別子が送り手の識別子と食い違えば、例外にする（`src/engine/worker-wire.ts`）

## 却下した案

- 配列をWorkerへ1度だけ送り、Workerが持つ。画面のスレッドの構造化複製が1度は残る（雪華で、CPUを4倍に絞って約3秒）ので、表を送る案より画面のスレッドの停止が長い
- Workerが表を自分で取得する。取得はメインスレッドの取得手段（`configureKanjiDirectLoader`）に依存しており、Workerにも同じ取得手段と非同期の依頼処理が要る。表の数百KBの複製で済むので、割に合わない
- 識別子を `Layout` のフィールドに持たせる。`{ ...layout }` で派生した配列が識別子を引き継ぎ、中身が違うのに同じキーになる。コンボを重ねた配列がこの形で作られる

## 結果

- 識別子の元の表が同じなら、配列の中身は同じになる。識別子は53bitのハッシュを含むので、別の表が同じ識別子になる確率は約2^-53である
- 派生した配列が元の配列と別のキーになる事は `src/engine/trace-key-table-identity.test.ts` が、Workerへ表を1度だけ送る事と、Workerを立て直した時に送り直す事は `src/engine/worker-client.test.ts` が確かめる
- 打鍵の記録のWorker（`src/app/record/`）は、この仕組みに乗せていない。依頼のたびに入力を送り、Worker内で中身のキーを作る
