# ADR-0031: 表による解析の表の元に、利用者のテキストを足し、表は計算用Workerの依頼で作る

- 番号: ADR-0031
- 日付: 2026-11-28（PRの日付）
- 状態: 採用

## 背景

ADR-0030は、標準のコーパスの表で解析する経路を決めた。その結果の節に、利用者のテキストから表を作る経路を判断に含めないと書いた。issue #96の受け入れ条件には、利用者のテキストから表を作って解析できることが残っていた。

ADR-0030は、メンバーの解決に評価に渡すテキストを使わず、固定の最小のテキストで解決すると決めた。評価に渡すテキストで解決する案の却下の理由は、使わない入力のためにTraceを作って長いテキストで計算が重くなることと、読みに直せないテキストで値に関係のない失敗が出ることだった。

利用者のテキストの表には、標準のコーパスに無い問題がある。

- 読みと文節の区切りが、利用者のテキストごとに、実行時に決まる。同梱の表は、作った時の分割器と辞書の版が固定している
- 利用者は読みを直せる。今の解析は、直しを当てた読みで測る
- 数え上げの時間が、テキストの長さに比例する。選べる次数は、テキストごとの統計で決まる
- 抽出のキーは、表の識別子・取得元のsha256・次数だけを持っていた。利用者のテキストでは、同じ識別子の表の中身が、テキスト・読みの直し・版で変わる

## 決定

- 表の元を、解析設定の `source`（`corpus` か `text`）で選ぶ。`text` の時の表は、アプリで選んだテキストから作る。選ぶ部品は、既存のテキストの選択とReadingChipを使い、表の元が `text` の時だけ出す（`spec/distance-model.md` §13.8）
- 読みは、評価に渡すテキストと同じ経路（読みのWorkerと `ReadingSource`）で、利用者の読みの直しを当てた読みのテキストを得る。文節の区切りは、分割器を読みに直す前の原文に当て、読みの位置へ写す経路（`computeSegmentation`）で得る。辞書の取得待ちは、他のAnalyzerと同じ `isWaitingForReading` の扱いにする
- 読みの直しは、利用者のテキストの表に当て、標準のコーパスには当てない。利用者のテキストは利用者のデータで、今の解析も直しを当てた読みで測る。標準のコーパスは、作り直した時に同じ表になることを保つ
- 数え上げは、計算の窓口に新しい依頼（`getNgramTable`。Workerの依頼の種類 `ngram-table`）を足し、Workerの中で行う。入力は、読みのテキスト・区切り・分割器と辞書の版・テキストの名前で、結果は選べる次数の表と統計の量を持つ `NgramTableSet`。同梱の表も同じ入れ物（`ngramTableSetOfFile`）にして、1つの次数を取り出す入口を共有する。Workerへの依頼は1度に1件で、数える間も画面の操作は止まらない
- 表の中身を見分ける値（`contentKey`）を抽出のキーに入れる。標準のコーパスは取得元のsha256と分割器・辞書の版、利用者のテキストは、読みのテキストと区切りの非暗号の照合値と長さ、分割器と辞書の版で作る。読みの直し・テキスト・版のどれが変わってもキーが変わる
- 数える次数の上限は、同梱の表と同じ5にする。選べる次数と既定の次数は、そのテキストの統計から §13.5の規則で決める。解析設定が選ぶ次数が選べない時は、その表の既定の次数で解析する
- メンバーの解決は、ADR-0030のまま、固定の最小のテキストで行い、Traceを作らない。選んだテキストは、表を作る入力にだけ使う
- 読みに直せないテキストは、表の状態に載せる。表の元が `text` の時に、次のように出す
  - 辞書を読み込めなかった: 漢字を読みに直さず、読みに直せなかった漢字で走りを切って表を作る。条件の要約に、辞書を読み込めず漢字を読みに直していないことを出す
  - 日本語でないテキスト: 分割器が日本語のモデルだけを持つので、表を作らず、値を出さない
  - 分割器か表の作成に失敗した: 値を出さず、表を作れなかった旨を出す
  - 数えられる文節が無い: 値を出さず、その旨を出す
  どの場合も、配列・Setupの対象の解決は失敗しない。ADR-0030が却下の理由に挙げた「値に関係のない失敗」は、対象の失敗としては出ず、表の状態に限られる
- 「加えた変更」の文は、表ごとに持つ（`NgramTableAsset.changesText`）。標準のコーパスの文を、利用者のテキストの表に出さない

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 抽出の中で表を作る（表の元のテキストを抽出の入力にし、Workerの抽出が数える） | 選べる次数が表を作った後にしか分からず、次数の選択肢を出すために、抽出の前に表を知る必要がある。次数とメンバーごとの計算で、同じ数え上げを繰り返さない仕組みも別に要る |
| 主スレッドで数える | 長いテキストで画面の操作が止まる。数え上げの時間はテキストの長さに比例する |
| 評価に渡すテキストでメンバーを解決する（ADR-0030の却下した案） | 表は評価に渡すテキストのTraceを読まないので、Traceを作る費用が無駄になる。ADR-0030の理由は変わらない |
| 利用者の読みの直しを、利用者のテキストの表にも当てない | 今の解析は直しを当てた読みで測る。同じテキストの2つの解析で読みが違うと、並べた時に差の原因が読みの違いか打ち方の違いか分からなくなる |
| 抽出のキーに、読みのテキストと区切りの全文を入れる | 長いテキストでキーの文字列が長くなり、メンバーごとの部分結果のキーにも入る。照合値と長さで足りる。照合値は非暗号の64ビットで、異なる入力が同じ値になるのは、照合値と長さが全部一致する時だけである。その時の害は、利用者自身のテキストの表1つで、抽出の結果を取り違えることに限る |
| 辞書を読み込めなかった時に、表を作らない | 他のAnalyzerは、漢字を読みに直さずに数値を出し、その旨を示している。表も、読みに直せない漢字で走りを切れば作れる（`docs/corpus-ngram.md`「系列」）。読みに直していないことは条件の要約に出る |

## 結果

- 同梱の表の値と、今の解析の値は変わらない。`test/fixtures/analyzer-regression.json` は動かさない
- 選べる次数は、利用者のテキストでは短いと0次だけになりやすい。1次が選べるには、続きが1種類の文脈の出現の割合が上限0.1以下である必要がある
- 数え上げは、1度に1件のWorkerの依頼で行う。長いテキストの間、ほかのペインの依頼はその終わりを待つ
- 表の作り直しはテキストの編集のたびに走る。結果は、メインスレッドに入力の中身のキーで4件まで写して、同じ入力へ戻る時は引き直す
